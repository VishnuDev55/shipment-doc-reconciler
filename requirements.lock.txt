# WHICH FILE IS WHICH, and why three exist
#   requirements.txt        direct runtime deps, pinned. What the Dockerfile
#                           installs. Nothing test-only.
#   requirements-dev.txt    requirements.txt + the dev tools, pinned. What CI
#                           and `make setup` install.
#   requirements.lock.txt   THIS FILE. The complete resolved environment, exactly
#                           as pip reported it.
#
# WHY BOTH A PINNED DIRECT FILE AND A FULL LOCK EXIST
# requirements.txt pins only what the code imports directly, so pip is still
# free to choose transitive versions. That is what makes the Dockerfile small
# and readable, but it means two clones a month apart can resolve different
# transitive versions and only one of them is the one the 709 passing tests ran
# against. This file is the answer to "what did we actually test": it is the
# environment docs/AUDIT.md finding R8 asked for ("requirements.txt is entirely
# ranged with no lockfile").
#
# To reproduce the validated environment exactly:
#   python -m venv .venv
#   .venv/Scripts/python.exe -m pip install -r requirements.lock.txt
#
# Note the lockfile is NOT what the Dockerfile installs: it contains the dev
# tools (pytest, ruff, mypy, coverage, pyflakes, pre-commit and their deps),
# which must stay out of the production image. It is a diagnostic and
# reproducibility record. To get a deployable runtime-only lock, create a clean
# venv from requirements.txt alone and freeze that.
